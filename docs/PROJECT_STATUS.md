## Architecture in one screen
- Modular monolith; each bounded context is `app/modules/<name>/{models,schemas,repository,service,router}.py`.
- **Multi-tenancy** = Postgres **row-level security**. Tenant-scoped tables extend `TenantScopedBase` and carry a `tenant_isolation` RLS policy (applied in their migration); repos also filter `tenant_id` explicitly (so the SQLite test suite, which has no RLS, is still isolated).
- **Global/cross-tenant tables** extend `AuditedBase` (no RLS): network, groups, messaging, notifications, marketplace, research, news, oauth_states, webauthn_challenges.
- **Auth**: JWT access + rotating refresh tokens; `get_current_user` in `app/core/deps.py` decodes the JWT (fast path) and also resolves `vsk_` **API-key** bearers. Access tokens carry `sub`/`tid`/`scopes`/`email`.
- **Pluggable seams** (real + mock, env-selected, test-injectable): storage, payments, notification channels, webhook transport, OAuth client, WebAuthn verifier.

Revoked sessions can no longer refresh. `/app/settings/security` "Active sessions" section (device string parsed from UA, "This device" badge, per-session + "sign out other devices").

## Matters: Indian court record + both sides' counsel (0033)
- `matters` now carries what Indian registries actually use: **CNR** (the 16-char Case Number Record, the stable key across re-numbering and transfer), case type/number/year, **filing vs registration** number and date, court level + establishment + state/district, coram, cause title, acts/sections, next & last hearing with purpose, and disposal.
- **`matter_advocates`** (tenant-scoped + RLS) records counsel *per side*. `PartySide` (`ours`/`opposing`/`other`) is deliberately separate from the cause-title role, because the firm may act for petitioner or respondent. `MatterParty` gained the same `side`. `GET /matters/advocates/opposing/{name}/history` answers "have we faced this counsel before?".
- **eCourts seam** `app/core/ecourts.py` (`ECourtsClient` protocol + `set_ecourts_client`), with endpoints `POST /matters/ecourts/lookup` (read-only preview), `/ecourts/import` (file it, splitting sides via `our_side_role`), and `/{id}/ecourts/refresh` (registry fields only — never clobbers title, client, assignment or notes).
- **There is no official public eCourts API.** The default provider is `UnconfiguredECourtsClient`, which returns a clear 503 rather than inventing data; no scraper ships here (the case-status pages are CAPTCHA-gated and a ToS question). `VS_ECOURTS_PROVIDER=sample` gives deterministic fabricated records for local UI work and is **refused in production**. Connecting a licensed feed means writing one adapter — see FUTURE_DELIVERABLES.

## Research corpus in production (5.66M)
- **Supreme Court**: 38,366 reported judgments (SCR), 1950–2026, via `ingest_scr_judgments`.
- **High Courts**: 5,626,224 eCourts *order* records — Punjab & Haryana 1,866,684, Allahabad 3,368,898, Delhi 390,642 — via `ingest_hc_judgments` (knows all 25 HCs; `--list-courts`). Both `metadata.parquet` and `metadata-mobile.parquet` are read: the mobile file is not a duplicate (44% overlap, ~72k unique records), and the overlap dedupes on `source_ref`.
- **`citation` is now nullable** (0034): order records have none. Uniqueness moved to a partial index; rows without a citation are keyed by `source_ref` (`court:cnr:date`), which makes the loader idempotent. **Any schema reading judgments must treat `citation` as optional** — a `citation: str` response field turned every search into a 500.
- **Search needs trigram indexes on all four searched columns** (0034 + 0035): `case_name`, `citation`, `headnote`, `keywords`. With only one, the planner filtered 5.6M rows per query (26 s); with all four it builds a BitmapOr (~28 ms; API 31.5 s → 0.15 s). They match `ILIKE`, *not* `lower(col) LIKE …`.
- Enrichment applies to Supreme Court rows only (it filters on that bucket's URL); fetching millions of HC order PDFs is not practical, so those carry the registry's `description` as a snippet instead of a headnote.
- **Structured, ranked search (0036):** `case_type`/`case_number`/`case_year`/`cause_title` parsed from registry titles, `judge_text` normalised to bare names (one judge = one facet value across `MR. JUSTICE X` / `HON'BLE … X` / `Justice X`), and a generated weighted `search_vector`. `GET /research/judgments` returns a page `{items, total}` ranked by `ts_rank_cd` with `<mark>`ed snippets, accepting Google-style syntax; `GET /research/judgments/facets` counts court / year / case type / judge / outcome for the same filters. Research page redesigned around a hero search box and a facet sidebar. **Bounded for a 5.6M-row corpus (2026-09-24):** the count is *capped* at 25,000 (`LIMIT cap+1`, stops early) and that cap alone decides ranked-vs-newest-first — the planner estimate is never trusted for that; `total_is_estimate` / `total_is_lower_bound` ("About N" / "More than N") tell the UI which figure it has; facets run under a 12 s `statement_timeout` and return `facets_partial` instead of a 504. Cold worst case on prod ~1–2 s, ranked queries ~0.1–0.5 s; the no-query landing list uses a matching newest-first index (0038: 6.4 s → 1.5 ms) and landing facets are windowed to 2 years. Registry placeholder "judges" ("Case is not allocated to court.") filtered. **All app pages are full-width** (`mx-auto w-full` roots; 33 pages incl. the client portal, 2026-09-24) — the research status line sits above the two-column grid so the first card and the facet card share a row.
- **Case information (2026-09-24, migration 0039):** an order record now carries `filed_on` (registry filing date), `petitioner` / `respondent` (split from the cause title, all courts), `petitioner_advocates` / `respondent_advocates` + `advocate_text` (parsed from the order's opening in all three registry formats — Delhi "…Appellant Through: Mr. X", Allahabad "Counsel for Petitioner :- X", P&H "Present: Mr. X, Advocate for the petitioners"; ~90% of Delhi orders, SC prose yields none by design), and Allahabad's neutral citation ("2023:AHC:117096"). `GET /research/cases/{cnr}` groups a case's orders into a timeline (parties, counsel union, judges, filed → first → latest order, latest disposal); the frontend has a case page (`/app/research/case/:cnr`), an "N orders in this case" chip on results, counsel on result cards, an **Advocate** facet + `advocate=` filter, and deep links (`?advocate=`, `?judge=`). **All 5,626,224 HC order links fixed** — the bucket keeps PDFs at `data/pdf/year=<decision year>/court=<code>/bench=<code>/<file>`, not the registry path the ingest stored (every link 404'd). Backfills: `backfill_case_parties` (pure Python over existing rows) and `backfill_filing_dates` (re-streams metadata parquet, staging table + `UPDATE … FROM`); run them **sequentially** — together they deadlock on shared rows (the parties script now retries 40P01, but don't rely on it).
- **Full text of orders (2026-09-24, migration 0040 — "option 1": text in Postgres, PDFs stay in the open-data bucket):** `judgments.full_text` + `text_extracted_at`, searched through its own GIN **expression** index `ix_judgments_full_text_fts` on `to_tsvector('english', left(coalesce(full_text,''), 300000))` — deliberately *not* folded into the generated `search_vector`, which would rewrite the 5.6M-row table under an exclusive lock (the 0036 outage). `_conditions` ORs the two vectors and Postgres BitmapOr's both indexes (verified with EXPLAIN); snippets highlight from the full text; ranking stays on the registry vector. `app/scripts/extract_order_text.py` streams the bucket's per-bench-year tar bundles (never to disk), runs pypdf in a process pool, writes in batches, and back-fills counsel from the text's opening where the metadata lacked it. Local pilot: 60/60 extracted, 0 empty, median 3.6k chars. **Production pilot: Delhi 2024 (54,291 orders, 4.5 GB) queued** behind the parties backfill (`backups/extract-delhi-2024.log`); `JudgmentCreate.full_text` lets users add text with a judgment; the detail page shows it collapsed. Storage: ~5–10 KB text per order (≈15–25 GB compressed for all 5.6M) vs ~95 KB per PDF (≈500 GB) — the reason PDFs are not stored.
- **Target corpus (decided 2026-09-25): Supreme Court + Allahabad (UP), Delhi, P&H, Uttarakhand — "full models"; the other 21 High Courts are on hold** (disk; user is arranging a 2 TB S3 bucket for the PDFs themselves). `infra/jobs/run_target_set.sh` runs it end to end: Uttarakhand (new court, bench `ukhcucis_pg`, code 5_15) via `run_new_court.sh`, then **Supreme Court text** (`extract_sc_text.py`: SCR volume PDFs; the reporter's headnote/index is cut with `sc_judgment_body` — publisher's copyright, *EBC v. Modak* — and only the judgment with its appearance block is stored; counsel via `parse_sc_counsel` for both SCR layouts), then order text for the four HCs newest-first. **Acts/sections** are now derived from text (`parse_acts_sections`: ~60 statute aliases, "Section 438 (Code of Criminal Procedure, 1973)" form, year variants merged, junk like "the Act"/"Chapter III of the Act" rejected) and written only where a row has none — the last 0% field for HC rows. The ingest writes case fields, parties, counsel, filing date and neutral citation directly now. Status at hand-off: 128,392 Delhi orders had text (from the earlier runner), all 5.66M rows have parties, 3.76M counsel.

  - **Client link.** `Matter.client_id` (FK → `clients`, SET NULL) beside the kept `client_name`; create/update/eCourts-import take `client_id` *or* a typed `client_name` (quick intake), and linking refreshes the name from the master while unlinking keeps it. `GET /matters?client_id=` lists a client's matters (shown on the client page with a "New matter for this client" link that pre-selects the client). Endpoints: `GET /matters/team/people`, `POST /{id}/team`, `PATCH /{id}/team/{mid}` (role / dates / rate override), **`POST /{id}/team/{mid}/handover`** (mid-matter change: ends the stint on a date with a reason — reassigned, left the firm, workload, client request, conflict… — and starts the successor in the same or a given role; the old row stays as history), `DELETE` for rows added by mistake, and **`POST /matters/team/transfer`** (`matter:manage`): every active stint of X on open matters → Y in one call, for "X left the firm". Matter create accepts `lead_counsel_id` + `team[]`.
  - **Fee arrangements** (`matter_fee_arrangements` + `matter_fee_milestones`, RLS): dated, one open at a time — a renegotiation closes the previous one the day before. Basis: **fixed** (lump sum), **per hearing** (effective vs non-effective/adjournment rates), **hourly** (matter default; team rate cards/overrides per person), **retainer** (monthly/quarterly/half-yearly/yearly, with what it covers), **milestone** (stage-wise), **hybrid** (any combination — e.g. fixed + per hearing), **pro bono**; plus fee cap, expenses-at-actuals and GST flags, agreed-on date and free-text terms. **No contingency/success fee** (BCI Rules Part VI Ch. II Rule 20) — stated in the UI. Milestones carry an amount or a % of the fixed fee and a trigger: `advance` (fires on save), `on_filing` / `on_pleadings` / `on_evidence` / `on_arguments` / `on_judgment` (matter stage changes), `on_first_hearing` (first hearing marked held), `on_closure` (matter closed), `on_date` (settled lazily on read when the date arrives), `manual` ("Mark reached"). Each fires **once**. UI has 30/30/30/10 and advance+balance templates.
  - **Fee events** (`matter_fee_events`, RLS) = what has fallen due and what invoices will be raised from next: milestone due, effective hearing (`per_hearing_fee` when a hearing is marked held), non-effective hearing (adjourned), the first retainer period, and manual entries (opinion, conference, drafting). Status `unbilled` → `invoiced` (reserved for the billing step; `invoice_id` column present) / `waived` (with restore). `GET /{id}/fees/summary` totals. Per-hearing events are raised once per hearing (guard on `hearing_id`).
  - **Counsel rate cards** (`counsel_rates`, RLS; module `app/modules/rates/`, `/rates`): per person and basis — hourly, per hearing, per day, per matter, per drafting/opinion, monthly retainer — with effective dates; a new rate for the same basis supersedes the open one; overlapping open rates are refused. ## Research corpus: real judgments, not generated ones
- **Legal Research now holds ~12,987 real Supreme Court judgments** (reporting years 2010–2026), ingested by `app/scripts/ingest_scr_judgments.py` from the `indian-supreme-court-judgments` AWS Open Data bucket (**CC-BY-4.0**, unauthenticated HTTPS — no scraping, commercially usable with attribution, which the stored `url` carries). The 5,000 generated judgments and their citation edges are gone.
- `--count N` means "the first N of the range", so **re-running is a no-op**, not another N rows. `--purge-sample` drops the generated judgments; `--clear` drops only ingested ones. Real vs generated rows are told apart by URL host.
- **Deliberately empty**: `headnote`, `acts`, `sections`, `keywords`, `bench`. They are not in the source, and a wrong headnote on a real citation is worse than none. `headnote` additionally carries legal exposure — s.52(1)(q)(iv) of the Copyright Act frees the *judgment text*, but *Eastern Book Company v. D.B. Modak* (2008) protects publishers' headnotes, so these must come from our own summarisation, never from SCC/Manupatra.
  - `bench` is blank because the source's `judge` column holds only the **authoring** judge (87% of 2025 rows have one name) — counting it labelled Supreme Court cases "Single Judge", which the Court does not do for reported judgments.
- **Enrichment** (`app/core/judgment_enrichment.py` + `app/scripts/enrich_judgments.py`) fills `acts`, `sections`, `keywords`, `bench` and `headnote` from each judgment's own PDF, restoring search quality and the Act/Section filters. Pluggable seam (`set_judgment_enricher`) so an LLM summariser can replace the rule-based extractor later. Resumable: only rows with no headnote are processed, so re-running continues where it stopped (`--force` redoes them).
  - Modern reports (≈2024+) print `List of Acts` / `List of Keywords` index blocks, which are used directly; older ones fall back to pattern matching plus a topic vocabulary.
  - `bench` and `judges` are rebuilt from the **coram** line (`[X and Y, JJ.]`), correcting the ingest-time gap where only the authoring judge was known. Role tokens (CJI/J/JJ) are not mistaken for names.
  - **The headnote is the Court's own disposal, extracted from the judgment body — never the SCR headnote**, which the PDFs credit to a named editor ("Headnotes prepared by: …") and which *EBC v. Modak* protects. Gutter letters (A–H) and the reporter's trailing result stamp are stripped.
- **Still empty:** Cites/Cited-by — there is no real citation graph (the old edges were random and were deleted). **Legal News remains 5,000 generated items**, untouched, since clearing it would empty that screen with no replacement (`seed_sample_corpus.py --clear` removes both).

## Identity: emails are globally unique (0032)

## WhatsApp hearing reminders and the VidhiSangh number — 20 October 2026
- **Sign-in codes come from VidhiSangh's own number**, +91 73411 00692 (display name "VidhiSangh", approved), with the authentication template `vidhisangh_otp` (code + Copy-code button). `VS_WA_OTP_TEMPLATE_PARAMS` names the template's body parameters, so the older Simsondesk template still works if ever needed.
- **Evening hearing reminders** (migration **0068**, global table `hearing_reminder_sends`): at about 7 pm IST (`infra/jobs/vidhisangh-hearing-reminders.{service,timer}`, `python -m app.scripts.hearing_reminders [--dry-run]`) each member who turned WhatsApp on and has a verified mobile gets one message, template `hearing_reminder` (utility), listing tomorrow's hearings on matters where they are lead counsel, assigned or an active team member (the creator when nobody is): "1. Title (case no.), court, 10:30 am, for purpose; 2. …", cut with "and N more". Scheduled and adjourned hearings of open matters only. The (member, day) row is claimed before sending, so a rerun never repeats; failures are recorded, not retried. Sending seam `app/core/whatsapp.py` (`set_whatsapp_sender` in tests).
- **Adding a mobile number to an existing account:** `POST /auth/me/phone/request` → WhatsApp code (purpose `verify`, bound to the requester) → `POST /auth/me/phone/verify`. A number already verified on another account is refused.
- **Frontend:** `shared/whatsapp-reminders` card — Settings → Notifications (replaces the "coming soon" WhatsApp row) and a dismissible prompt at the top of the Calendar while reminders are off; verifies the number inline, then switches on.
- **Fixed: date-times were saved as UTC.** `vs-date-input withTime` sent "2026-10-21T10:30" with no zone; the server read it as UTC, so a 10:30 hearing showed as 4:00 pm in India. The model now carries the device offset ("…T10:30+05:30") and a stored "…Z" value opens in local time (`shared/date-input/utc-offset.ts`). Hearings, news and calendar forms all use it.
- **WhatsApp sign-in survives leaving the app** to read the code: the code in progress is kept on the device until it expires or is used (`features/auth/whatsapp-pending.ts`), the sign-in screen reopens on WhatsApp, and app updates are applied only at launch (a `kill` delay blocks the plugin's install-on-background, `set()` at start-up).
